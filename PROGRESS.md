## What the site actually does (current architecture)
- Vite + React SPA, deployed as a Cloudflare Worker (not classic Pages) — `wrangler.jsonc` has
  both `assets` (the static build) and `main: src/worker.ts` (real backend logic for `/api/*`).
- **Current FX rates**: live client-side fetch, `src/lib/fxLive.ts`, from
  fawazahmed0/currency-api via jsDelivr CDN (free, no key, 200+ currencies, confirmed
  CORS-safe from real browsers). Falls back to a bundled offline snapshot if the fetch fails.
- **Historical FX rates ("Biggest currency movers" tab)**: as of 2026-08-24 this is a **static
  file**, `src/data/historical-fx.json`, NOT a live fetch. It's generated by
  `scripts/fetch-historical-fx.mjs` (fetches yearly snapshots from api.frankfurter.dev — ECB +
  50 central banks blended, free, no key, ~30 currencies) run via
  `.github/workflows/refresh-fx-history.yml` (manual `workflow_dispatch` or monthly cron).
  **Do not reintroduce a live client-side historical fetch** — that caused a real
  infinite-retry/flicker bug (a failed fetch was falsy, so a stale closure kept retrying every
  render). The static-file approach exists specifically to eliminate that whole bug class.
  To refresh the data: trigger the `refresh-fx-history` workflow via
  `POST /repos/bazzizazzi/fx-trip-compass2/actions/workflows/refresh-fx-history.yml/dispatches`
  with `{"ref":"main"}`, or just wait for the monthly cron.
- **"Cheapest right now" ranking**: Big Mac Index purchasing power (`src/lib/purchasingPower.ts`,
  `src/data/bigmac.json`). Real Economist data where available; GDP-regression estimate for
  currencies Economist doesn't cover, clearly labeled "est." in the UI (never shown identically
  to real data — this was a real bug found and fixed 2026-08-19).
- **Hidden gems**: `src/data/destinations.json`, 120 destinations. User-mandated ratio of
  hidden-gem : anchor-city is 5:1 to 10:1 (currently exactly 100:20 = 5:1). If adding more
  destinations, preserve this ratio — add hidden gems to dilute, don't remove anchors (removing
  anchors reintroduces the "100% hidden gem for this country" bug already fixed once).
- **Flights**: NOT connected to any real provider. `src/worker.ts` `/api/flights` and the
  frontend toggle ("Include flight cost in ranking") are fully wired end-to-end but always
  return `available:false` until a real key exists — this is intentional, not a bug. No fake
  flight prices are ever shown.
- **Activities (Viator)**: `/api/activities` in `src/worker.ts` is written per Viator's official
  Affiliate API docs (sandbox base `api.sandbox.viator.com/partner`, `exp-api-key` header) but
  has **never been live-tested** — this sandbox can't reach that domain directly. Nothing from
  Viator is rendered on any public page yet, so the noindex-for-scraped-content rule (see below)
  doesn't need to fire yet, but implement it the moment Viator content actually renders anywhere.
- **i18n**: `src/lib/i18n.tsx`, single file, 4 full locale dicts (en/he/es/fr), English is
  default. Every new UI string needs all 4 languages added together, never leave one as a
  silent English fallback.
- **Legal**: `/privacy`, `/terms`, `/methodology` routes (see `src/Root.tsx` for the
  no-router-library pathname switch). Content in `src/lib/legalContent.ts` and
  `src/lib/methodologyContent.ts`. Governing law = Israel, Tel Aviv courts (user-specified,
  done). **Two placeholders remain**: `[CONTACT EMAIL]` and `[COMPANY / INDIVIDUAL NAME]` —
  user is evaluating whether to pursue the site; once they buy a matching domain they'll
  provide both. This reminder is intentionally not user-facing, only in source/this file.

## User-mandated security/architecture rules (given 2026-08-19, apply to ALL future API work)
These came from the user directly and shaped `src/worker.ts` + `src/server/validate.ts`.
Any new backend integration (a real flights provider, Viator going live, etc.) must follow them:
- No API key/token/affiliate secret ever in the frontend bundle or committed to git. Server-side
  only, injected via GitHub Actions secrets → `wrangler secret put` at deploy time.
- Architecture is always `Browser → our Worker → Provider API` — the browser never calls a
  provider directly with a secret.
- Every user-supplied input (destination, dates, guests, star rating) must be validated against
  a whitelist/schema server-side, never trusted raw — see `validateSearchParams` in
  `src/server/validate.ts`. Destination is resolved against `destinationWhitelist.ts`, never a
  free-text string, which is also the SSRF defense (outbound provider URLs are built from our
  own stored data, never from raw client input).
- Every outbound provider call needs a timeout + limited exponential-backoff retry (see
  `fetchWithTimeout`/`fetchWithRetry` in `worker.ts`) and basic rate limiting (naive per-isolate
  in-memory limiter exists; recommend the user also enable Cloudflare's dashboard Rate Limiting
  Rules for defense in depth — not yet asked of them).
- Webhooks (if any provider ever sends one): verify signature if the provider supports it,
  guard against replay, make the handler idempotent. Not yet relevant — no provider sends
  webhooks to us yet.
- Affiliate tracking: opaque random click IDs only (`src/lib/affiliateTracking.ts`,
  `crypto.randomUUID()`), NEVER email/name/IP/phone in any tracking or subid parameter. The
  live Trip.com link already follows this.
- Don't store personal data beyond genuine business need; don't send customer data to a
  provider that doesn't need it; define retention for any future logs/analytics.
- Payments: user's explicit preference is NOT to handle payment on this site at all for now —
  flow is User → our comparison → affiliate link → provider's own site → payment happens at
  the provider. Do not build in-house checkout/payment handling unless the user explicitly
  changes this instruction.
- Only use documented, permitted API access for any provider — no scraping, no undocumented
  endpoints, no bypassing rate limits, no credentials not explicitly given by the user.
- noindex: the moment any page renders a provider's unique content verbatim (Viator tour
  descriptions/reviews, etc.), that page needs `<meta name="robots" content="noindex">` to
  avoid Google penalizing duplicate/scraped content. Not needed yet (nothing renders yet).

## History of major fixes this project (for context, not action items)
- Switched historical FX from a broken live-fetch architecture (flicker/infinite-retry bug —
  `historical[years] || ...` treated a failed fetch as falsy and retried every render) to the
  static-file approach described above. Root-caused and fixed 2026-08-24.
- Fixed a flight-toggle false-positive: the capability probe was missing a required `minStars`
  param, causing a 400 validation error that got misread as "provider available," enabling the
  toggle with zero real data behind it → empty results. Fixed by sending all required params
  and only trusting `available === true`.
- Fixed Big Mac "est." mislabeling: GDP-estimated prices were shown identically to real
  Economist data with no visual distinction. Now carries a visible "est." badge + tooltip.
- Removed a confusing dual-index picker (Big Mac vs. partial Eurostat PLI) per explicit user
  feedback ("stupid, remove it") — reverted to single Big Mac metric while the composite score
  (see above) is being built properly.
- Removed a redundant "Best in [Month]" badge — it was always true by construction since the
  month filter already hard-excludes non-matching destinations before any card renders.
- Fixed HTML caching: the SPA shell had no cache-control override, so browsers could serve a
  stale cached page indefinitely after a new deploy. Worker now forces `no-cache,
  must-revalidate` on the HTML shell specifically (hashed JS/CSS assets still cache normally).
- Verified FX accuracy against 3 independent live sources early on (GBP/USD, GBP/JPY, GBP/TRY)
  after the user flagged suspected errors — all three were actually correct; the user's
  fact-checking tool had used outdated reference rates. Good practice to re-verify with fresh
  sources rather than assume either side is right when there's a discrepancy.
